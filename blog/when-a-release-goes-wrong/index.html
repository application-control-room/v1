When a release goes wrong: a five-step incident playbook

November 9, 2026 · 6 min read
ACR team
Application Control Room

Every team that ships will eventually ship something broken. What separates a five-minute blip from a lost evening is rarely the bug itself. It is how quickly you notice, how much of the damage you can stop before the fix exists, and whether your users know what is going on.

This is a playbook for that moment. It has five steps, and at each one we point to the part of ACR built for it.

1. Detect: hear about it before your users tell you​

The worst way to learn about an incident is a support ticket. Set up signals that reach you first.

  • Alert rules. In Alerts, create rules for the things that really mean trouble: a new or regressed error issue, an error spike, p95 latency above a threshold, poor Web Vitals, a release whose crash-free sessions drop, or an app that stops sending data. Send them to email, Slack, Discord, Teams or a webhook. Cooldowns and mute windows keep a noisy rule from paging you every minute.
  • Uptime checks. Uptime checks your public URLs every 5 to 60 minutes and opens an incident after the number of consecutive failures you choose, then resolves it when checks recover.
  • Releases. If you set appVersion in your SDK, Releases shows adoption, crash-free sessions and newly introduced issues for each version. A bad release stands out in the comparison.

Tip: test every alert rule against your app's real traffic before you rely on it. A threshold that fires all the time gets muted; one that never fires is not protecting you.

2. Contain: stop the damage before the fix exists​

This is the step most teams skip, because without the right levers the only option is "deploy a fix". You have faster options, from smallest to largest blast radius:

Turn the feature off. If the broken code is behind a feature flag, switch the flag's Enabled off, or lower its rollout. Everyone receives the default value on the next poll.

Get users off the bad version. If the problem is in the browser bundle and you have already deployed a fix, open the release policy in Controls and set a minimum version. In force mode, tabs below it reload once onto the new code. Or send a one-shot reload command to every open tab.

Clear what is stuck. A bad service worker or a corrupted cache entry can keep serving broken assets after you fixed them. A clear cache command tells every browser running the app to drop Cache Storage, service workers, local storage, session storage, IndexedDB or script-readable cookies (you choose which), and optionally reload. Each browser applies it at most once, and the command history shows how many reachable browsers have applied it.

Close the doors. If the problem risks data, such as broken payments or writes that corrupt records, turn on maintenance mode. Browser SDKs cover the app with a full-page screen. Add your own user ids to the exemption list so your team can keep testing in production. On servers, the Express middleware and the NestJS guard answer 503 with Retry-After when you enable them, while health checks keep passing.

Quiet the noise. In the rare case that your own telemetry is part of the problem, such as a log loop flooding the network, lower the sample rate, raise the minimum log level, or use the collection kill switch.

Controls, announcements and commands need the admin role, because they affect every user at once. Decide in advance who on your team holds it, so you are not hunting for an admin mid-incident.

3. Communicate: tell people before they guess​

Silence makes every incident feel worse. A short message buys a lot of patience.

  • Announcement banner. Publish an announcement with severity warning or critical, a message such as "Payments are delayed. Your orders are safe, and we are working on it.", and optionally a link to a status page. Every visitor sees it on the next poll. Schedule an end time, or end it yourself when things are fixed.
  • Maintenance message. If you closed the doors, the maintenance screen is your message. Say what is happening and roughly when you expect to be back. The expected time is informational; maintenance never ends by itself.

4. Fix: from symptom to line​

Now that the damage is contained, you can fix the bug calmly instead of under fire.

  • Errors groups occurrences into one issue with a readable stack trace, the affected users and the versions it appeared in. If you upload source maps through CI, browser stack traces point to your original code instead of the minified bundle.
  • Logs let you filter by level, source, message or trace id around the time of the incident, and tail new lines live while you reproduce.
  • Performance shows whether a route became slower, at p50, p95 and p99, if the problem is speed rather than failure.

Ship the fix with a new appVersion, so you can see it take over in Releases.

5. Recover: reopen carefully, then learn​

Undo your containment in the reverse order you applied it, and watch as you go:

  1. Check the fix yourself first. If you used maintenance mode, your exempt user id lets you use the real app.
  2. Turn maintenance off, or bring the flag back to a small rollout instead of jumping straight to 100%.
  3. End the announcement, or replace it with a short "resolved" message.
  4. Watch Errors and Releases until the new version carries most sessions and the issue stops recurring.
  5. Resolve the alert incident.

Then write down what happened while it is fresh: how you noticed, how long containment took, and what would have made it faster. Usually the answer is one more flag around a risky change, or one more alert rule that would have fired sooner.
