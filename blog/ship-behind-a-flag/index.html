Ship behind a flag: gradual rollouts without a redeploy

November 3, 2026 · 6 min read
ACR team
Application Control Room

The safest deploy is one that changes nothing. Merge the new code, ship it switched off, and decide later, from a console, who gets to see it. If it misbehaves, switch it off again. No revert, no hotfix, no second deploy.

That is what feature flags are for. This post explains how flags work in ACR and walks through a rollout recipe you can use on your next feature.

Decouple deploying from releasing​

Without flags, deploying code and releasing a feature are the same event. Every deploy is a bet on everything inside it, and the only way to back out is another deploy.

With a flag, they come apart:

  • Deploy whenever the code is ready, with the feature off.
  • Release when you choose: to your team, then a small share of users, then everyone.
  • Roll back by changing a number in the console. The change reaches running apps on their next poll, about a minute later.

Creating a flag​

In the ACR console, open Flags and create one. The fields that matter most:

FieldWhat it does
KeyThe name your code reads, such as new-checkout. It cannot change later, so pick it carefully
Typeboolean, string, number or json
EnabledA disabled flag always returns the default, whatever else is configured
ValueWhat people inside the rollout or allow-list receive
Default valueWhat everyone else receives
RolloutThe percentage of users who receive the value, from 0 to 100
Always on for these usersUp to 100 user ids that always receive the value

Developers and above can create and edit flags; everyone on the app can read them.

Reading a flag in code​

Every ACR SDK can read flags. In React:

TSX
import { useFlag } from '@lib-acr/react';

export function Checkout() {
  const newCheckout = useFlag('new-checkout', false);
  return newCheckout ? <NewCheckout /> : <OldCheckout />;
}

In a plain browser app it is acr.flag('new-checkout', false). On a server, the Node.js SDK does not know who the request is for, so you pass the user:

TypeScript
const enabled = acr.flag('new-checkout', false, { userId: req.user?.id });

The second argument is the fallback your code uses when the flag does not exist yet, or before the first snapshot arrives.

Two properties make this cheap enough to use everywhere:

  • No network request per check. The SDK keeps the latest control snapshot in memory and evaluates flags locally. A flag check is a function call, not an API call.
  • It keeps working offline. If ACR is unreachable, the SDK uses the last values it saw. If it never saw any, your fallback wins.

Why each user keeps the same result​

A rollout is only useful if it is stable. If a user saw the new checkout on one page load and the old one on the next, your rollout would be a source of bugs, not a safety net.

ACR evaluates a flag in a fixed order:

  1. Missing or disabled → the default.
  2. The subject is your identified user id, or the visitor's anonymous id if you have not called identify().
  3. Subject in the allow-list → the value.
  4. Otherwise, a stable hash of the flag key and the subject gives a bucket from 0 to 99. A bucket below the rollout percentage receives the value; everyone else gets the default.

Because the bucket depends only on the flag key and the subject:

  • The same person always lands in the same bucket, on every device where you identify them, in the browser and on the server.
  • Raising the rollout only adds people. Going from 25% to 50% keeps everyone who already had the feature and adds the next 25 buckets. Nobody flips back and forth.
  • Lowering it removes people in the reverse order, which is exactly what you want when something looks wrong.

The rollout recipe​

Here is a sequence that works for most features.

1. Ship it dark. Create the flag with Enabled on, Rollout 0%, and your team's user ids in the allow-list. Deploy the code. Nobody outside your team sees anything.

2. Test in production. Use the real app, with real data and real traffic around you. This catches what staging never does: production config, third-party scripts, real browsers.

3. Open it to 5%. Watch Errors for new issues and Performance for slower routes. Give it long enough to see a normal day's traffic.

4. Step up: 25%, then 50%. Keep watching. If you run a release at the same time, compare its crash-free sessions against the previous version.

5. Go to 100%. Leave the flag in place for a while as a kill switch.

6. Clean up. Once you are confident, remove the flag check from the code and delete the flag. Flags that live forever become a second, invisible configuration system.

If anything goes wrong at any step: switch Enabled off. Every user gets the default on the next poll, about a minute later, and immediately when a browser tab comes back into focus.

Beyond on and off​

Boolean flags cover most rollouts, but ACR flags can do more:

  • Typed values. A number flag can tune a limit, a string flag can pick a copy variant, and a json flag can carry a small configuration object of up to 4 KB.
  • Targeting rules. Ordered conditions on user or visitor attributes decide who receives which value.
  • Weighted variants. Serve more than two named variants in fixed proportions.
  • Scheduled changes. Plan a rollout step, a value change or an enable for a specific time.
  • Experiments. Give a flag two or more variants, pick a conversion event such as purchase_completed, and Experiments compare conversion rates and tell you when the difference is statistically significant.

One rule: no secrets in flags​

Flag values are delivered to browsers. Anyone can read them in developer tools. Use flags to decide what to show, never to carry API keys, tokens or anything else you would not print on the page.

Try it on your next feature​

Pick the riskiest thing you are building this week, wrap it in useFlag or acr.flag, and ship it at 0%. The full reference is in Feature flags. If you have not connected an app yet, start with Connect your first app.
