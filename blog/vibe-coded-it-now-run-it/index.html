You vibe coded it in a weekend. Now run production the same way.

October 27, 2026 · 5 min read
ACR team
Application Control Room

Building software has never been faster. You describe a screen, an AI assistant writes it, you look at it in the browser, you ask for a change, and an hour later you have something that used to take a sprint. People call it vibe coding, and whatever you think of the name, the result is real: more apps reach production, built by smaller teams, sometimes by one person.

Then the app goes live, and the vibe stops.

The gap after launch​

Production asks questions that the build loop never did:

  • Is anyone actually using it? Which pages do they visit, and where do they drop off?
  • What is breaking right now, for whom, and since which version?
  • That new feature you generated on Tuesday: can you turn it off without regenerating and redeploying everything?
  • Users are stuck on an old bundle. How do you get them onto the new one?
  • You need to take the app down for ten minutes. Do you have a maintenance page? Does it reach people who already have the app open?

When you build fast, you also accumulate code you did not write line by line. That is fine while you are iterating in your editor. In production it means you need to see what that code is doing, and you need a way to change its behaviour faster than you can change the code.

Most teams answer this with a stack of tools, each with its own setup, its own dashboard and its own learning curve. For someone who just built an entire app in a weekend, that is a strange step backwards.

Run production like you built it​

The thing that makes vibe coding feel good is a tight loop: describe → see → adjust. ACR gives you the same loop for a running app.

See it: one install, instant signal​

Add one SDK and the app starts telling you what is happening. For a React app it is a provider around your root:

TSX
import { ACRProvider } from '@lib-acr/react';

createRoot(document.getElementById('root')!).render(
  <ACRProvider
    config={{
      apiKey: import.meta.env.VITE_ACR_API_KEY,
      endpoint: import.meta.env.VITE_ACR_ENDPOINT,
      appVersion: '1.0.0',
    }}
  >
    <App />
  </ACRProvider>,
);

That one change gives you visitors and sessions, page views, Core Web Vitals, and uncaught errors grouped into issues with stack traces. The ACR console has copy-ready snippets for React, Angular, plain browser apps, Node.js, Express and NestJS, so this is also an easy thing to hand to your assistant: "add the ACR SDK using this snippet" is a one-shot prompt.

When you want more, describe what matters in your own words and record it:

TSX
import { useACREvent } from '@lib-acr/react';

const track = useACREvent();
track('checkout_started', { cartSize: 3 });

Adjust it: switches instead of redeploys​

This is where ACR differs from a dashboard. Every change below happens from the console, reaches running apps in about a minute, and needs no new build:

You want to…In ACR
Hide a feature that is misbehavingTurn its feature flag off
Try a feature on yourself firstPut your user id in the flag's allow-list, rollout 0% for everyone else
Release it graduallyRaise the rollout: 5%, 25%, 50%, 100%
Take the app down brieflyTurn on maintenance mode, with your own id exempt
Tell users somethingPublish an announcement banner
Get everyone onto the new versionSet a release policy, or reload every open tab
Fix a broken service worker or cacheSend a clear-cache command to every browser

Wrapping new work in a flag is a one-line habit that pays off immediately:

TSX
import { useFlag } from '@lib-acr/react';

const newCheckout = useFlag('new-checkout', false);
return newCheckout ? <NewCheckout /> : <OldCheckout />;

The flag is evaluated inside the SDK, so this check is free and works offline. When you ask your assistant to build a risky feature, ask it to put the feature behind a flag too. Shipping switched off becomes your default, and "undo" stops meaning "regenerate and redeploy".

Guardrails you get for free​

Fast builders tend to skip the boring parts. ACR has sensible defaults for the ones that bite in production:

  • Keys that are safe in a browser. Browser apps use a publishable key that only works from the origins you allow. Server secrets are shown once, and the browser SDK refuses to run with one, so a secret cannot slip into a bundle unnoticed.
  • Privacy by default. Query strings are stripped, sensitive keys like passwords and tokens are redacted, email addresses in free text are masked, and visitor IP addresses are never stored.
  • Telemetry that cannot crash your app. SDK calls never throw, buffers have a fixed size, and if ACR is unreachable your app keeps working.
  • Roles when you add people. Invite a collaborator as a viewer or developer; only admins and owners can flip controls that affect every user.

A Monday morning, the ACR way​

Here is what running a small app looks like once this is in place:

  1. Open the app's Overview: connected, live visitors, nothing alarming.
  2. Glance at Errors: one new issue since last night's release, 14 users affected.
  3. Open it: the stack trace points at the new address form, behind the new-address-form flag.
  4. Set that flag's rollout back to 0%. Within a minute, nobody sees the broken form.
  5. Ask your assistant to fix the bug, paste in the stack trace, deploy when ready.
  6. Turn the flag back on for yourself, check it, then roll it out again.

No pager drama, no hotfix rush, no full redeploy just to hide a button. Building and running feel like the same activity again.
